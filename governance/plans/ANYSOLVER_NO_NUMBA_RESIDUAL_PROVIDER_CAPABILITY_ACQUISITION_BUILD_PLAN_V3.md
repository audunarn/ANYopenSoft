## 2. Acyclic trust, acquisition, and build-input DAG

The V2 `provider_build_input_manifest.json` is split into three immutable layers.
No layer contains its own hash. Each layer's SHA-256 is accepted externally and
passed as a literal argument to its consumer.

### 2.1 Layer T: pre-acquisition trust bootstrap and expected-input authority

- Path:
  `Q\provider-manifests\provider_trust_and_expected_inputs.json`
- Schema:
  `anysolver.no_numba_residual.provider_trust_and_expected_inputs/1`
- Producer:
  a future content-addressed `freeze_provider_trust_inputs.py`, created via
  `apply_patch` and run only under separate metadata authority.

Layer T is frozen before any artifact acquisition. It contains no acquired-byte
receipt and no signature-verification result. It freezes:

- exact Canonical verifier-bundle and Ubuntu-keyring expected sources,
  filenames, lengths, digests, package/release identities, and independent
  bootstrap authorities;
- required Canonical/Ubuntu signer fingerprints from V2;
- exact expected versioned rootfs, signed-checksum, InRelease, Packages-index,
  `.deb`, `actions/python-versions`, attestation, PyPI/sibling/build, source
  archive, and wheel-build input identities;
- exact URL/effective-URL, redirect, length, digest, architecture/tag, and
  security/yank policies;
- expected verifier path/hash and trust-root path/hash after acquisition;
- exact schemas and paths for every receipt and verification result;
- no result claiming that a signature or digest has already been verified.

Verifier bootstrap precedes signature validation in this exact order:

1. Acquire verifier bundle and keyring as ordinary expected inputs under Layer T.
2. Validate their bytes against the independent bootstrap digest/Authenticode or
   upstream release authority frozen in Layer T.
3. Validate verifier executable member inventory, ELF closure, version, and
   executable hash without using the verifier being bootstrapped.
4. Extract verifier/keyring into fresh read-only verifier paths.
5. Publish immutable verifier-bootstrap receipts.
6. Only then invoke the bootstrapped verifier for rootfs signed checksums and
   InRelease signatures.

Failure before step 5 means no signature validation may run. The verifier can
never establish its own trust.

## 5. Namespace confinement and process audits

### 5.1 Builder base/init/background audit

Immediately after PB03 and before PB04, the accepted host coordinator obtains a
read-only base process receipt from the isolated builder. It records every
`/proc` PID, PPID, PGID, session, namespace inode set, start time, state,
executable, command line, UID/GID, cgroup, and open listening socket.

The accepted seed disables systemd and unregistered boot commands. The only
permitted base processes are the exact WSL init/service processes frozen after
PB03 independent review. Any daemon, package process, shell, network listener,
host interop process, prior task child, zombie, or unknown background process
blocks PB04.

Before and after every PB04-PB22 operation, `build_provider.py` repeats base and
background audits and requires ordinal equality to the accepted base identities,
except for the positively owned command namespace/process tree. It separately
audits namespace init, direct child, descendants, PGID/session, zombies,
listeners, and residuals.

### 5.2 Mandatory namespace wrapper

Every PB04-PB22 payload runs under exact hash-allowlisted `unshare` with fresh
mount, PID, network, IPC, and UTS namespaces, a fresh `/proc`, and an exact
command cgroup. User namespace behavior is frozen in Layer I; no ambient user
namespace fallback is allowed.

The namespace init:

- establishes PDEATHSIG before payload exec;
- verifies parent identity;
- mounts no host path;
- permits loopback only with no route or DNS;
- applies exact read-only input and write-root mount policy;
- reaps all descendants;
- records namespace inode identities;
- exits only after zero descendant/residual proof.

No task payload or its descendants may execute outside these namespaces. The
outer accepted `unshare`/namespace-init pair is part of the producer's exact
descendant allowlist and is audited before and after each command.

### 5.3 All-outcome Linux finalization

Normal success, expected nonzero, policy mismatch, launch error, signal, timeout,
producer exception, and coordinator interruption all require durable intent,
start, transcript, namespace, process-tree, termination, filesystem,
network/mount, and result/failure records under `L`. Timeout signals only the
owned namespace/cgroup/process group, waits/reaps, and proves zero residual PID,
PGID, session, namespace child, cgroup member, zombie, listener, or background
drift. Unproven state is infrastructure failure.

## 6. Windows Job Object and coordinator-loss containment

PB03 and PB23 are Windows host operations. Their sole producer creates a Windows
Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, assigns the exact launched
`wsl.exe` process tree, records job/accounting identities, and launches no other
unregistered child.

Before launch, the coordinator starts the content-addressed
`provider_host_watchdog.py` as its only safety descendant with literal arguments:

- coordinator PID/start identity;
- exact builder distro name;
- exact accepted `wsl.exe` path/hash;
- completion-token path/hash contract;
- unique watchdog transcript/process/result paths;
- operation deadline and import/export target paths.

The watchdog is not placed in the coordinator's kill-on-close Job Object. It
waits for either a durably fsynced valid completion token or coordinator loss/
deadline. It performs no normal build work.

On PB03/PB23 timeout or coordinator loss, the watchdog:

1. Records durable failure intent and observed coordinator/Job Object state.
2. Waits for Job Object kill-on-close processing and records owned Windows
   process exits.
3. Executes exactly one scoped
   `wsl.exe --terminate ANYsolver-ProviderBuilder-Ubuntu-24.04-82a9db28-v1`.
4. Never invokes `wsl --shutdown`, unregister, another distro name, retry, or
   cleanup.
5. Waits for the terminate command and inventories `wsl --list --running`.
6. Audits Windows processes/command lines for the owned coordinator, watchdog,
   `wsl.exe`, import/export operation, and target distro.
7. Records builder name/import-path state, export partial/final state, Job Object
   accounting, terminate exit, residual processes, and any unproven service
   state.
8. Publishes one durable watchdog result and stops.

The watchdog itself is bounded by the outer authority and has a frozen timeout
that leaves V2's 10-minute reserve. If the watchdog cannot prove the distro
stopped and all owned Windows processes exited, the outcome is infrastructure
failure and all state is preserved for governance.

On normal PB03/PB23 completion, the coordinator durably publishes and fsyncs the
completion token before exiting; the watchdog verifies it, records no recovery
action, publishes its final process audit, and exits. The coordinator cannot
mark success until the watchdog final is valid.
