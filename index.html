Open engineering ecosystem · updated 2026-10-06

Open tools. Connected engineering.

Independent Python packages and desktop applications for structural, marine and offshore engineering. Geometry, meshing, loads, solvers and visualization each live in one canonical repository and connect through public contracts — so you can model, mesh, load and analyze stiffened plate fields, shells and frames.

02 — Project directory

The ecosystem, repository by repository.

Filter by category or search by name. Each card names the repository's role in one or two lines.

  • ANYfem

    Active development Application

    Standalone finite-element application for shell and beam structures. Qt workbench by default; pressure definitions in Python or CSV/Excel arrive through ANYloads.

  • ANYstructure

    Maintained Application

    Desktop steel-structure design application for stiffened plate fields and cylindrical shells, with its own Tk-based FEM interface.

  • ANYsolver

    Owner — solver mathematics

    Finite-element calculation engine for shell and beam elements, with linear static and nonlinear solution routes. Nonlinear-shell and general-contact routes are in development.

  • ANYbuckling

    Owner — buckling rules

    Prescriptive and semi-analytical buckling rules as a standalone engine, without a GUI.

  • ANYloads

    Active development Loads

    Load definitions and evaluation, independent of solver, geometry and mesh. Pressure fields can be defined as expressions, code or tables.

  • ANYgeometry

    Owner — geometry

    Owns geometry, topology, persistent identity, tolerances, spatial indexing and intersections. Recent work adds exact angular lifts for cylinder boundary rulings.

  • ANYmesh

    Owner — discretization

    Owns discretization and mesh generation, consuming qualified geometry contracts. Published as the Python distribution ANYmesher (anymesher). A provisional prepared planar network mesh consumer is in development.

  • ANYmaterial

    Owner — materials

    Owns material definitions, validation and canonical conventions, including provenance.

  • ANYtimeseries

    Owner — time series

    Independent owner of time-series processing.

  • ANYfileIO

    Canonical owner — interchange

    Canonical owner of interchange syntax and neutral file semantics.

  • ANYfileio-occt

    Optional adapter

    Optional OCCT interchange backend adapter.

  • ANYio

    Retired publishing

    Legacy interchange repository. Its duplicate publishing path is retired; ANYfileIO is canonical. Kept for history and compatibility reference.

  • ANY3dView

    Owner — view contracts

    Backend-neutral 3D scene and view contracts. Hosts and platforms need their own interaction and identity checks.

  • ANYtk3D

    Adapter

    Tk presentation adapter for ANY3dView contracts, for embedding 3D views in Tkinter desktop applications.

  • ANYworkspaceAI

    Orchestration product Private repository

    Workspace orchestration with a typed engine/workbench, built on the ecosystem's public engineering APIs.

  • ANYintelligent

    Research Private repository

    Machine-learning research for the ANY ecosystem. Engineering calculations remain with the dedicated solver and buckling packages.

  • ANYopenSoft

    Coordination home

    This portal: governance, ecosystem documentation and public coordination for the ANY ecosystem.

03 — Ecosystem ownership map

One owner per domain. Everyone else consumes.

Domain truth lives in its canonical repository and is consumed through public contracts. Dependencies point from owners to consumers — never the reverse.

Contracts the map encodes

  • Single ownership. Each domain — geometry, meshing, loads, materials, interchange, solver mathematics, buckling rules, view contracts — has exactly one canonical repository.
  • Public contracts only. Consumers use public owner APIs; copied owner models, reverse imports and coordinate-derived replacements are architectural defects.
  • Clear failures. Unsupported or ambiguous input produces a typed, actionable error — never a silent fallback.
  • Boundaries are SI. SI units internally; conversion happens once, at ingestion or display.
  • Identity is persistent. Model-bound IDs are never guessed from coordinates or silently reused.
  • Qualification is narrower than implementation. A downstream application cannot broaden an owner's qualified scope.
